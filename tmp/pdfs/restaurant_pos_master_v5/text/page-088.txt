C5 — Table status does not necessarily reflect a
QR order awaiting confirmation
Finding: II.5.15 states "transitions to Occupied normally accompany an
Order creation," and I.35 states QR orders enter PendingConfirmation
before being Accepted. Neither document specifies whether a QR order
still in PendingConfirmation (customer submitted, restaurant has not
yet confirmed) causes the associated Table.current_status to move to
Occupied, or whether it stays Available/Reserved until confirmation.
This matters operationally: if a walk-in customer is seated at a table that
already shows Available because an unconfirmed QR order hasn't flipped
the status yet, a double-booking / seating conflict is possible — the exact
class of race condition this document set otherwise takes great care to
prevent (I.14, I.37).
Fix (recommended addition to II.5.15 and I.35): A QR order entering
PendingConfirmation moves the associated Table to Reserved (not
Occupied — the table isn't physically occupied by a walk-in yet, but it
is not free for other seating either), and only moves to Occupied once
the order is Accepted. If the order is Rejected, the table reverts to
Available (unless another concurrent process has since changed it, per
normal optimistic-concurrency rules). This closes a real seating-race gap
using the state machine that already exists — no new states are needed.
