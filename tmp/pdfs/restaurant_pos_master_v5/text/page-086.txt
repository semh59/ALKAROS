C2 — Order pre-reservation states not fully
covered by portion_reservation_status
Finding: The order_items.portion_reservation_status fix (III.6.2,
Corrections v5 §4.2) defines only two pre-reservation values —
NotApplicable and NotReserved — with NotReserved documented as
"order
item still Draft." But the Order lifecycle (II.5.1 / I.8) has three
pre-Accepted states for channel-validated orders: Draft →  Submitted →
PendingConfirmation →  Accepted. Reservation happens at Accepted
(I.24).
It is unclear what portion_reservation_status value an order item holds
while its parent order sits in Submitted or PendingConfirmation (e.g. a
QR order awaiting restaurant confirmation, per I.35) — currently it would
default to NotReserved, conflating "not yet reserved because still in
early draft" with "not yet reserved because awaiting explicit confirmation
that could still be rejected."
Fix: This is a low-severity naming gap, not a data-integrity risk (both
cases correctly have no portion_reservations row yet), but for reporting
clarity, consider renaming NotReserved to PendingAcceptance or adding a
fourth value; a UI showing "not reserved" for a QR order sitting in
PendingConfirmation for 10 minutes could confuse staff into thinking
nothing is happening. Recommend: keep the two-value model but
document
explicitly that NotReserved spans Draft, Submitted, and
PendingConfirmation uniformly — no schema change required, only a
documentation clarification in III.6.2.
