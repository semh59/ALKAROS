0.2 Why part-prefixed numbering
Each source document had its own independent numbering starting at 0/1.
Concatenating them verbatim would have produced multiple unrelated
"Section 5", "Section 14", "Section 39" etc. across the merged file — a new,
entirely avoidable defect. Every heading below is therefore written as
I.N, II.N, or III.N. Cross-references between parts use the same
prefixed form (e.g. "see II.5.6 Bill closure") so a reader can always tell
which part a citation belongs to without ambiguity.

I.26A Bill ↔  Payment Closure Invariant
Bill-level money fields have explicit ownership:
Bill.payable_amount = final amount that must be covered.
Bill.allocated_amount = SUM of valid
PaymentAllocation.allocated_amount for the Bill.
Bill.paid_amount = SUM of allocated amounts belonging to payments
that are in a financially final state (Approved and not subsequently
reversed/refunded).
Bill.change_amount = SUM of cash change actually returned for the
Bill; it is not part of the amount allocated to the Bill.
Payment.allocated_amount is a cached/derived operational value equal to
the SUM of that Payment's PaymentAllocation rows. It is never an
independently authoritative amount.
A Bill may become Paid only when:
paid_amount == payable_amount
AND all required payment allocations are valid
AND no required payment is Pending / Unknown / Declined / 
Cancelled
AND no unresolved fiscal/reconciliation condition blocks closure
For split payment, there is no SplitPayment tender. The Bill is closed from
the composition of its individual approved tenders. (Duplicate-allocation
protection at the database level: III.8.2, Corrections v5 §1.)

PART II — DOMAIN SPECIFICATION
II.0 Purpose
This part defines the core domain model, invariants, state machines,
command boundaries, and operational rules for the restaurant POS
product. It is intentionally positioned before the database schema (Part III)
because the schema must follow domain rules, not the other way around.
The product is a single-branch restaurant POS with: local-first operation,
waiter PWA, cashier terminal, kitchen printers, Hugin T300 fiscal/payment
device, QNB eSolutions invoice integration, meal card settlement, QR
ordering, online ordering, daily menu + portion pool, customer accounts,
audit, backup, reconciliation.
Microservices are not part of the target architecture.
II.1 Domain principles
II.1.1 Source of truth

===== PAGE 35 =====

PostgreSQL is the authoritative source of truth. SignalR, printer buffers,
external provider callbacks, QR sessions, and UI state are not authoritative.
II.1.2 English codebase
Every domain term in code must be English. Examples: Order, Bill,
BillAllocation, Payment, PaymentAllocation, DailyMenu,
DailyMenuItem, RecipeVersion, ProductionBatch, PortionReservation,
KitchenTicket, PrintJob, MealCardSettlement, CustomerAccount,

II.1.3 No silent destructive actions
The following cannot be silently deleted: financial transactions, fiscal
documents, audit events, order history, production history, backup history,
reconciliation history. Corrections must be represented as new domain
actions.
II.1.4 Immutable historical references
Anything that affects historical calculation must be snapshotted or version-
referenced. Examples: order price snapshot, recipe version reference,
production batch reference, payment allocation reference, fiscal reference,
meal card settlement reference.

II.3 Core domain model
II.3.1 Product
A product represents a sellable item or a configurable operational item in
the restaurant. Attributes: name, SKU, category, tax profile, active state,
base pricing, printer routing hint, stock mode, modifier compatibility,
availability behavior.

===== PAGE 37 =====

Stock mode:Untracked, QuantityTracked, PortionTracked,
RecipeDerived.
Examples: Cola → QuantityTracked; Chicken Meal → PortionTracked +
RecipeDerived; Napkin → Untracked; Tea → QuantityTracked or
RecipeDerived depending on operational policy.
II.3.2 Order
The canonical channel-independent sales request. Origins: cashier, waiter,
QR, online provider. Order is not bill, not payment, not fiscal document, not
kitchen ticket.
Responsibilities: capture intent, capture channel, capture customer/table
context, track item states, trigger inventory reservation at the correct state,
trigger kitchen routing, support cancellation paths, preserve price
snapshot.
II.3.3 Bill
Customer-facing financial summary of one or more orders or order parts.
Bill is not payment. Responsibilities: calculate payable amount, support
splits, support allocations, support closure, support re-open/void policy
only if explicitly allowed, represent adisyon/checkout context.
II.3.4 Payment
A tendering event with a specific method and provider. Methods: cash,
bank card, meal card, customer account, split payment as a composition
model, not a separate tender type. Payment is not bill closure by itself.
II.3.5 PaymentAllocation
The mapping between a payment event and the amount assigned to a bill
allocation or payable segment. Exists because: one payment can settle part
of a bill; one bill can be settled by many payments; cash tendered can
exceed allocated amount and generate change; payment callbacks can be
partial or uncertain. Duplicate-protection enforcement: III.8.2.
II.3.6 DailyMenu
The operational menu for a specific business date: what is available today,
how many portions are planned, what price applies today, whether the item
is open/closed/sold out. Not the same as the product catalog.

===== PAGE 38 =====

II.3.7 Recipe & RecipeVersion
A recipe is the conceptual definition. A recipe version is the historical,
immutable operational definition used for a specific production batch or
cost basis. Recipe version must never be rewritten for historical accounting
purposes.
II.3.8 ProductionBatch
A concrete production event. Must always reference exactly one recipe
version — one of the most important immutability rules in the product.
II.3.9 PortionReservation
Temporary lock of a prepared portion for an order or channel. Not the same
as consumption.
II.3.10 MealCardSettlement
The operational accounting layer between the restaurant and meal card
provider. Not the same thing as customer current account.
II.3.11 CustomerAccount
The restaurant-side receivable relationship with a customer/company. Used
for periodic invoicing and deferred payment scenarios.
II.3.12 FiscalDocument
A provider/device-backed legal or operational fiscal artifact. Not the same
thing as bill or payment.
II.3.13 KitchenTicket
A production instruction set derived from one or more orders and routed by
station. Not a print job. Composed of KitchenTicketItem rows, each with
its own finer-grained state — see II.5.7A.
II.3.14 PrintJob
The physical printing task. A failed print job must not destroy the order or
the kitchen ticket.
II.3.15 ReconciliationCase

===== PAGE 39 =====

Created when two or more authoritative states diverge. Examples: payment
approved but fiscal unknown; online provider accepted but local order
rejected; print job lost but order exists; meal card settlement mismatch;
QNB invoice timeout.
II.3.16 Table (new subsection — closes prior audit gap B7)
The physical/operational representation of a seating unit. Table is not Bill,
not Order. A Table's current_status reflects seating availability, not
financial state. See II.5.15 for the formal state machine and its deliberately
lighter audit/reconciliation treatment relative to financial entities.

II.6 Core business rules
II.6.1 Table transfer
A table transfer moves the operational association of an open order/bill
from one table to another. Rules: source table history remains; target table
history remains; order id remains; bill id remains; transfer is audited;
transfer is transactional; concurrent edit protection applies.
II.6.2 Table merge
A table merge joins multiple tables operationally. Rules: no history deletion;
no silent overwriting; merged relationship is auditable; open orders remain
intact; merge can be reversed only via explicit follow-up operation.
II.6.3 Split bill
Split bill is designed in V1 and operationally enabled in V1.2 (design-vs-
operational distinction spelled out at I.11). Supported concepts: item split,
amount split, mixed payment split, equal split as UI convenience over
amount split. Rules: total allocations cannot exceed bill payable amount;
rounding must be deterministic; the same item cannot be allocated to two
owners unless explicit split-by-subitem rules exist; split state must remain
auditable.
II.6.4 Bill closure
A bill is paid only when the sum of valid allocated payment values equals
the payable amount and all required payment/fiscal states are acceptable.
Acceptable: cash/bank card/meal card/customer account, each Approved.
Not acceptable for final closure: pending, unknown, declined, cancelled
payment, or unresolved reconciliation case.

===== PAGE 45 =====

II.6.5 Bill ↔  Payment closure and overpayment
Money concepts are deliberately separated:
Bill.payable_amount: authoritative amount due.
Bill.allocated_amount: sum of valid PaymentAllocation rows.
Bill.paid_amount: sum of allocated amounts belonging to financially
final payments.
Bill.change_amount: sum of actual cash change returned.
Payment.allocated_amount: cached/derived sum of its
PaymentAllocation rows.
PaymentAllocation.allocated_amount: authoritative allocation record.
A Bill is Paid only when:
paid_amount == payable_amount
AND all required allocations are valid
AND no required payment remains Pending / Unknown / Declined / 
Cancelled
AND no blocking fiscal/reconciliation condition remains 
unresolved
SplitPayment is a composition pattern, not a tender type.
Bill payable: 950
Cash tendered: 1000
Payment allocated: 950
Change returned: 50
The payment event, allocation, and change are three different concepts.
II.6.6 Payment allocation integrity
PaymentAllocation is the authoritative bridge between a Payment and the
amount it covers on a Bill or BillAllocation. Rules: a Payment may have one
or more allocations; an allocation may cover a BillAllocation or a direct
payable segment; Payment.allocated_amount is derived from allocation
rows; Bill.allocated_amount is derived from all valid allocations; no
allocation may exceed the remaining payable amount of its target;
duplicate callbacks must not create duplicate allocation rows — enforced
via a partial unique index for the direct-to-Bill case (bill_allocation_id
IS NULL) plus a compound unique index for the BillAllocation-targeted

===== PAGE 46 =====

case, in addition to a required idempotency_key uniqueness constraint
(III.8.2, Corrections v5 §1); refunds/reversals create compensating
financial records — historical allocation rows are not rewritten.
II.6.7 Recipe versioning
A production batch must always point to an immutable recipe version.
Rules: a recipe may have many versions; production batch references
exactly one version; historical cost reporting uses the referenced version;
recipe version must not be overwritten in place.
II.6.8 QR ordering
Default policy: restaurant confirmation. Rules: QR submission creates a
pending customer order request; the restaurant may confirm or reject; only
accepted orders reserve portions and proceed operationally; QR must not
expose internal network resources; QR must not be able to create
uncontrolled stock consumption.
II.6.9 Inventory reservation
Rules: reservation is not consumption; available stock cannot become
negative; reservation must be atomic; release returns to availability; waste
is final; restaurant and online channels share the same portion pool.
II.6.10 Print idempotency
Rules: one logical kitchen print request must not generate uncontrolled
duplicates; retry must be idempotent or deduplicated; paper-out or offline
printer must queue the job, not lose the order; print failure is recoverable.
II.6.11 Reconciliation
(Renumbered from the erroneous duplicate "§6.10" in the prior draft —

Rules: any mismatch between authoritative states generates a
reconciliation case; mismatches are not silently ignored; reconciliation state

C1 — [STRUCTURAL] Migration order creates a
forward/circular FK reference
Finding: III.32 (Migration strategy) orders schemas as:
1. identity  2. catalog  3. table management  4. orders  5. 
billing ...
But III.5.2 (table_mgmt.tables) declares:
current_order_id uuid FK nullable (references orders.orders, 
...)
current_bill_id  uuid FK nullable (references billing.bills, 
...)
table_mgmt (step 3) is migrated beforeorders (step 4) and billing
(step 5) — a table cannot declare a foreign key to a table that does not
exist yet. This is a genuine migration-ordering defect, not merely
cosmetic: running the migrations in the stated order will fail at the
tables table creation step.
Fix: Two acceptable options —
1. Add the current_order_id / current_bill_id columns to tables
without an FK constraint at initial migration time, then add the FK
constraints in a later migration step once orders and billing exist
(ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID,
then
VALIDATE CONSTRAINT after backfill). This is the standard pattern for
resolving circular cross-schema dependencies.
2. Reorder migration steps so orders and billing are created before
table_mgmt — but this is awkward because orders.orders.table_id
also
references table_mgmt.tables, producing a genuine circular
dependency
between the two schemas either way.
Recommended: Option 1 (deferred/NOT VALID FK) — update III.32 and
III.5.2 to state explicitly that tables.current_order_id /
current_bill_id FKs are added in a second migration pass after orders
and billing exist, not in the initial table_mgmt migration.

C2 — Order pre-reservation states not fully
covered by portion_reservation_status
Finding: The order_items.portion_reservation_status fix (III.6.2,
Corrections v5 §4.2) defines only two pre-reservation values —
NotApplicable and NotReserved — with NotReserved documented as
"order
item still Draft." But the Order lifecycle (II.5.1 / I.8) has three
pre-Accepted states for channel-validated orders: Draft →  Submitted →
PendingConfirmation →  Accepted. Reservation happens at Accepted
(I.24).
It is unclear what portion_reservation_status value an order item holds
while its parent order sits in Submitted or PendingConfirmation (e.g. a
QR order awaiting restaurant confirmation, per I.35) — currently it would
default to NotReserved, conflating "not yet reserved because still in
early draft" with "not yet reserved because awaiting explicit confirmation
that could still be rejected."
Fix: This is a low-severity naming gap, not a data-integrity risk (both
cases correctly have no portion_reservations row yet), but for reporting
clarity, consider renaming NotReserved to PendingAcceptance or adding a
fourth value; a UI showing "not reserved" for a QR order sitting in
PendingConfirmation for 10 minutes could confuse staff into thinking
nothing is happening. Recommend: keep the two-value model but
document
explicitly that NotReserved spans Draft, Submitted, and
PendingConfirmation uniformly — no schema change required, only a
documentation clarification in III.6.2.
C3 — account_transactions.amount sign convention never
specified
Finding: The new generated direction column (III.18.3, Corrections v5
§4.4) derives Debit/Credit purely from transaction_type, and
explicitly returns NULL for Adjustment with the comment "sign carried by
amount." This reveals a pre-existing, still-unresolved ambiguity: is
account_transactions.amount always stored as a positive magnitude

===== PAGE 87 =====

(with
transaction_type/direction carrying the sign), or can it be stored
signed (negative for Refund, positive for Charge)? Neither the
original schema nor this merge states a convention. If different parts of
the application assume different conventions (one path stores
Refund →  amount = -50, another stores Refund →  amount = 50 relying
on
direction alone), balance calculations (current_balance,
customer_account_snapshots.balance) will silently double-count sign.
Fix (recommended addition to III.18.3):amount is always a positive
magnitude; direction (derived) and transaction_type together
determine the signed effect on current_balance. Balance calculation
formula: current_balance = SUM(CASE WHEN direction = 'Debit' THEN
amount WHEN direction = 'Credit' THEN -amount ELSE amount END) (with
Adjustment
carrying its own explicit sign in amount, per the existing NULL
direction case — this is the one deliberate exception and must remain
clearly documented as such).
C4 — payment_allocations.idempotency_key scope not
specified for internally-generated allocations
Finding: III.8.2's fix makes idempotency_keynot null unconditionally.
This is correct and necessary for allocations arising from external
provider callbacks (Hugin T300 response, meal card provider webhook)
where
retries are a real risk. But it is not stated whether a cashier-initiated
manual cash allocation (no external callback involved at all — cashier
taps "apply payment" once, no network retry possible) must also synthesize
an idempotency_key, and if so, what it should be derived from.
Fix: State explicitly (addition to III.8.2): for any allocation not
originating from an external callback, the application layer must generate
a client-side idempotency key (e.g. {terminal_id}:
{operator_session_id}: {monotonic_sequence}) at the moment the UI
action is taken, before the
server call — the same discipline already required for waiter PWA
submissions (I.15) — so that a double-tap or a retried HTTP request from an

===== PAGE 88 =====

unstable local network connection cannot create a duplicate allocation
either. Without this, the partial-unique-index fix in C1/§1 only protects
against external-provider duplication, not UI-level double submission,
which is arguably the more common real-world case in a touchscreen POS.
C5 — Table status does not necessarily reflect a
QR order awaiting confirmation
Finding: II.5.15 states "transitions to Occupied normally accompany an
Order creation," and I.35 states QR orders enter PendingConfirmation
before being Accepted. Neither document specifies whether a QR order
still in PendingConfirmation (customer submitted, restaurant has not
yet confirmed) causes the associated Table.current_status to move to
Occupied, or whether it stays Available/Reserved until confirmation.
This matters operationally: if a walk-in customer is seated at a table that
already shows Available because an unconfirmed QR order hasn't flipped
the status yet, a double-booking / seating conflict is possible — the exact
class of race condition this document set otherwise takes great care to
prevent (I.14, I.37).
Fix (recommended addition to II.5.15 and I.35): A QR order entering
PendingConfirmation moves the associated Table to Reserved (not
Occupied — the table isn't physically occupied by a walk-in yet, but it
is not free for other seating either), and only moves to Occupied once
the order is Accepted. If the order is Rejected, the table reverts to
Available (unless another concurrent process has since changed it, per
normal optimistic-concurrency rules). This closes a real seating-race gap
using the state machine that already exists — no new states are needed.
C6 — Cascading settlement status update is
application-responsibility only, same risk class as
the already-fixed direction column
Finding: III.17.2's fix defines meal_card_payments.settlement_status
with the rule "moves to Settled when the parent
meal_card_settlements.status reaches Settled." Unlike

===== PAGE 89 =====

account_transactions.direction (fixed in C3/III.18.3 as a GENERATED
ALWAYS column precisely to prevent drift), there is no equivalent
database-level enforcement here — nothing prevents a settlement moving
to
Settled while some of its child meal_card_payments rows are still
sitting at IncludedInSettlement because an application bug forgot to
bulk-update them. This is the same class of risk already identified and
fixed for direction, but not yet applied here.
Fix: Either (a) add a database trigger/constraint that rejects a
meal_card_settlements.status →  Settled transition unless all referenced
meal_card_payments.settlement_status values are already updated in the
