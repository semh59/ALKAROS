## 0. Real findings surfaced incidentally while researching this plan (not test gaps — actual product issues, fix separately from writing tests)

These were discovered by the research passes while reading code to build the
scenario catalog, not by running anything. Each needs its own small follow-up
task, independent of whether/when the corresponding E2E spec gets written:

1. **`src/Clients/Cashier/wwwroot/payments/split-payment/split-payment.js` never reads the new `unsettledPayment` field.** This week's `V1-RMD-258` remediation made the backend (`DualScreenApplication.Payments.cs`) genuinely fail-closed against a duplicate BankCard attempt (a real 409/typed rejection server-side) — but the CLIENT still only tracks the "Unknown" lock in an in-memory `state.locked` variable set during the current page load. Net effect: a page reload no longer risks a double charge (the server blocks it), but the UI will show a generic error instead of the intended "mutabakat gerekiyor" banner after a reload, which is confusing/wrong UX for a real cashier. **Needs its own small frontend task**, not just an E2E spec pinning current (incomplete) behavior.
2. **`src/Clients/WaiterPwa/wwwroot/js/screens/tables.js`'s `TABLE_STATUS` dictionary falls through to the raw, untranslated status code** (`TABLE_STATUS[table.status] || { label: table.status, cls: '' }`) if the backend ever sends a status value this client's map doesn't know about. This is a live `docs/UI_STYLE_GUIDE.md` §3 risk sitting in already-shipped code — not yet confirmed to have actually fired in production, but the fallback itself is the bug. **Needs a proper Turkish fallback label**, not just a test that documents the current risky behavior.
3. **`src/Clients/PosTerminal/src/routes/RelaySettings.tsx`'s `ConnectorStateLabels` is a plain untyped `Record<string, string>`**, unlike the TypeScript-exhaustive `healthStatusLabels` map used elsewhere in the same client for the same class of problem (backend enum → Turkish label). If the backend ever adds a 4th `connectorState` value, this screen can silently render the raw enum string to a manager. **Needs to be converted to the same exhaustive-union pattern** already established and working correctly elsewhere in this codebase (`System Health`'s own health-status map is the reference implementation to copy).
4. **CustomerWeb's Order Entry note field (`order-entry.js`) has no visible client-side length guard**, unlike the equivalent free-text note fields in WaiterPwa/Cashier (both capped at `maxlength="200"`). Not yet confirmed whether this is actually exploitable (the server may still cap it), but worth a quick, separate check before assuming parity with the staff-facing clients.
5. **CustomerWeb's Order Entry has no visible re-check of a pre-existing `submissionId` on page load** (`init()`). A guest who closes the tab mid-order and reopens the same link may see a stale empty cart with no indication their order already exists/was already submitted, rather than resuming the poll. Needs a code read to confirm whether this is a real gap or whether some other mechanism (e.g. a fresh `bill.html` visit) is the intended recovery path — flagged, not yet fixed.

## 2. Principles (unchanged from v1, still binding)

- Real Postgres (`alkaros-test-pg`, port 55432), real built Host binary serving the client's own real files, real Chromium (`@playwright/test@1.63.0` pinned — `1.48.0` hangs silently under modern Node) — no mocks, mirroring every existing suite exactly.
- A spec that never catches a real bug on its first honest run should be treated with suspicion, not confidence — every existing suite in this repo has found a real shipped defect on day one.
- One spec file per real user journey, numbered.
- Load/concurrency testing is a separate later phase per client, not bundled into functional specs.
- A confirmed-safe finding ("I tried to break X, couldn't, because of Y lock/constraint") is exactly as valuable as a confirmed-bug finding — write both.

## 4. Sequencing recommendation (revised, now cost/value-ranked with the deep pass's own findings)

1. **Phase 1 — Cashier split-payment (§3.1.J), smallest, highest immediate value.** Directly follows this week's own audit. Do the BankCard-never-fakes-success and reload-lock scenarios FIRST, specifically, ahead of everything else in this whole plan — they're the cheapest possible tests with the highest possible blast radius if wrong.
2. **Phase 2 — WaiterPwa offline-queue permanent spec + kiosk-lock security regressions (§3.2).** Both are real, previously-proven-then-un-pinned fixes; both are cheap relative to their value; neither needs new infrastructure.
3. **Phase 3 — the cross-client flagship scenario (§3.4)**, once Phase 1's Cashier harness and a minimal PosTerminal harness both exist — this single test validates this week's biggest architectural fix (the payment-aware table-topology TOCTOU close) as a real end-to-end guarantee, which no other test in this plan does.
4. **Phase 4 — PosTerminal Kitchen KDS (§3.3)**, prioritizing the role/permission cross-matrix test and the merged-ticket-cancel regression first — this feature's own history has the highest density of past real bugs caught only by manual audit in this entire research pass.
5. **Phase 5 — PosTerminal Tables/floor-plan + Reservations (§3.4, remainder) and Settings/Display/NFC/Authorization (§3.5)** — large, recommend a dedicated scoping/task-breakdown session before writing specs, same as v1 already recommended; this deep pass's own breakdown is the starting hypothesis for that session, not a final task list.
6. **Phase 6 — CustomerWeb (§3.6)** — now unblocked immediately (the "needs an investigation spike" caveat from v1 is resolved; the harness question is answered) — recommend pulling this earlier than v1's Phase 4 placement, given it's the one surface an actual paying guest's own phone renders and currently has zero coverage of any kind, not even unit tests.

## 5. Known environment gotchas (unchanged from v1, now with 3 new Playwright-specific ones from this pass)

- Real test Postgres: `alkaros-test-pg`, port **55432**, `postgres`/`postgres`.
- Required env vars (`ALKAROS_KITCHEN_STATION_ID` etc.) missing → bare, bodyless 500 (DI failure, not a normal exception path).
- Docker/WSL resource exhaustion under heavy parallel Chromium — `wsl --shutdown` + relaunch + `docker start` is the documented fix, not a regression signal.
- Full `MigrationComposition` suite (~160+ tests, ~10 min) has been killed by host memory pressure in multiple sessions this week alone — budget accordingly for a much larger E2E surface.
- **New**: `page.fill()` on a React controlled input can silently no-op (confirmed once already, on Token Terminal Settings' QR-paste field) — use `pressSequentially()` for any React-controlled text input a spec needs to type into programmatically.
- **New**: time-driven UI (Customer Display's pairing-code expiry, 7s auto-conceal, 10s stale-data timeout; WaiterPwa's 3-minute idle-lock) needs `page.clock` clock-mocking or a shortened test-only fixture value, never a real multi-second-to-multi-minute wait.
- **New**: several "current state" claims across these clients are explicitly documented as session-local-only, not server-truth (Screensaver Settings is the clearest example) — a spec must assert the DOCUMENTED behavior, not assume every settings-style screen reflects real server state on reload the way most of them do.
