# Sensitive envelope, secrets and outbox: known limits

Recorded by the BuildingBlocks audit (V1-RMD-596). These are deliberate gaps, each with the reason it is open and what would close it.

## Envelope AAD is not bound to the record (596-B020)

The authenticated data of a `SensitiveEnvelope` covers the field classification, the creation time and the key id, but not the record it belongs to. A database writer could copy one valid envelope onto another row of the same table and it would still decrypt. Closing it means adding the record id to the authenticated data, which makes every stored envelope unreadable unless the envelope format is versioned and existing rows are re-encrypted. It needs database write access to exploit, so it is held until a versioned migration is planned.

## Secret names collide across `-` and `_` (596-B025)

`EnvironmentVariableSecretProvider` turns `a-b` and `a_b` into the same variable (`ALKAROS_SECRET_A_B`). Today's names use hyphens only (`envelope-master-key`, `yemeksepeti-client-id`), so nothing collides; new names must keep to lower-case words joined by hyphens. Several modules also register their own `ISecretProvider`; the last registration wins and all are the same type.

## Small hardening items not done (596-B026)

Memory zeroing of decrypted key bytes, an injectable clock (`TimeProvider`) for retention hooks, the `MaxAge = Zero` edge of the retention hook, the fixed requeue reason text, one 404 text for two cases, schema constraint names and an index on `idempotency_keys.expires_at`, parsing of an `in_flight` status in `OutboxStore.ReadMessage` (claims read only `pending` rows today), and thread-safety of the in-memory secret provider (no consumers) are low-impact and unscheduled.

## Not wired in production (596-B012, 596-U18)

`SecretStartupValidator`, `IRetentionPolicyHook`/`MaxAgeRetentionPolicyHook`, `PayloadRedactor` and `InMemorySecretProvider` exist and are tested but nothing in the running host uses them. A missing envelope key is therefore found on first use, except in the QR relay connector, which checks it at start. Real data deletion is done by the privacy retention execution module, not by these hooks.

## `build/project-manifest.json` is a snapshot (596 documentation finding)

The file was generated by V1-FND-001 and lists projects that no longer exist while omitting newer ones. Only the plan audit checks that it exists; the real consistency check is `tools/project-manifest/project_manifest_tool.py` over the solution file and the disk. Do not read the JSON as the current project list.
