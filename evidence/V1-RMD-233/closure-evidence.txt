## Decision: "no balance row" stays UNLIMITED, not "0" (explicit, per task requirement)
`src/Host/DualScreen/DualScreenStore.cs` is NOT modified — the existing
"mapping with no balance row is excluded from the MIN(), leaving
RemainingCount null (unlimited)" behavior is CORRECT and INTENTIONAL,
confirmed by direct precedent already shipped elsewhere in the codebase:
`OrderDtoAssembler.WithAvailableStockAsync` (V1-RMD-143) does the exact
same thing in C# — its per-mapping loop `continue`s past a mapping with no
matching balance row, so if every mapping for a product lacks a balance,
`AvailableStockQuantity` stays null (unlimited), the identical outcome to
DualScreenStore's LATERAL join's MIN() silently ignoring NULL rows.
DualScreenStore.cs's own inline comment already references this exact
precedent ("MIN() ignores NULL rows on its own, so a mapping with no
default location or no balance row is silently excluded from the limiting
decision, same as that C# loop's own 'continue'").
Rationale for keeping "unlimited" rather than switching to "0": a mapping
that exists but has never had a stock_balances row (e.g. a brand-new stock
item awaiting its first physical count) is a data-entry gap, not proof the
product is out of stock. Showing "0" would hide the product from sale for
a reason the operator never intended or even knows about, whereas
"unlimited" matches what an unmapped product already shows and self-
corrects the moment a balance is recorded — no code change needed to fix
a data-entry gap once it's filled in.
