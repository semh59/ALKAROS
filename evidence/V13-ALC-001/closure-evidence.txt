## Scope executed
Implements PaymentAllocation persistence per V0-DOM-004's locked decision
record (docs/domain/payment-allocation-integrity.md): immutable
payment_allocations rows, same-bill, currency-equality, remaining-amount
and idempotency invariants, both at the application level and the
database level.

- `src/Modules/Payments/Allocations/Persistence/PaymentAllocation.cs`:
  immutable entity, constructor enforces amount > 0 (CORR:C4 — no
  negative/zero allocation ever exists).
- `PaymentAllocationExceptions.cs`: InvalidPaymentAllocationAmountException,
  CrossBillPaymentAllocationException, CurrencyMismatchAllocationException,
  OverAllocationException.
- `PaymentAllocationFactory.cs`: pure (no I/O) validation given an
  already-loaded Payment, Bill and the bill's already-allocated total —
  same-bill, currency-equality (transitively payment=bill), and
  remaining-amount (`amount <= bill.PayableAmount - alreadyAllocated`).
  Testable without a database (5 pure unit tests).
- `IPaymentAllocationRepository.cs` + `PostgresPaymentAllocationRepository.cs`:
  `AllocateAsync` is atomic and idempotent — a replay of an already-
  persisted idempotency key returns the existing row; a per-bill Postgres
  advisory lock (`pg_advisory_xact_lock(hashtext(...))`, same pattern as
  PostgresStockBalanceRepository) serializes concurrent allocation attempts
  against the SAME bill so the remaining-amount check can never race.
  Verified with a real concurrent-Task.WhenAll test, not just sequential.
- `PaymentAllocationPersistenceModule.cs`: a separate `IModule` (kept out
  of `PaymentAggregateModule.cs`, owned by V13-PAY-001).
- `database/migrations/V13/V13-ALC-001/123-payment-allocations.{up,down}.sql`:
  additive only. Two composite UNIQUE constraints on `payments.payments`
  ((payment_id, bill_id), (payment_id, currency_code)) and one on
  `billing.bills` ((bill_id, currency_code)) — each a strict superset of
  an already-unique column, restricting nothing already stored — enable
  `payment_allocations` to express the same-bill AND currency-equality
  invariants as real composite foreign keys, with NO trigger needed. Plus
  the idempotency-key UNIQUE constraint and the amount>0 CHECK.
  Over-allocation (a running SUM across sibling rows) has no equivalent
  static SQL constraint without a trigger; consistent with every other
  cross-aggregate money invariant in this codebase (Payment, Bill,
  BillItem all enforce these at the application level only, never via a
  trigger), it is enforced in `PaymentAllocationFactory` instead, proven
  against real Postgres through the repository (not a raw-SQL bypass).
- `tests/Modules/Payments/Allocations/Persistence/**`: new test project.
  5 pure factory tests (no DB) + 13 repository integration tests (real
  Postgres): round trip, idempotent replay, over-allocation through the
  real repository, a genuinely concurrent double-allocation race (proves
  the advisory lock, not just the sequential case), and 4 raw-SQL "database
  test" cases proving the composite FK/UNIQUE/CHECK constraints reject
  cross-bill, currency-mismatch, duplicate-idempotency-key and zero-amount
  inserts even if a future caller bypasses the factory entirely (same
  pattern as PostgresPaymentTests' own DatabaseRejects* tests).
