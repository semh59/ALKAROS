## Addendum (2026-09-18, same day): real bug found by an independent review
After V13-CSH-004 wired this handler to a real HTTP endpoint, an
independent review found that `HandleAsync` accepted `request.AmountDue`
as the approved amount without ever cross-checking it against the Bill's
own real remaining payable BEFORE opening the write transaction — only
`AllocateAsync`'s own later, lock-guarded check would catch an
over-claiming amount (correctly rolling back the whole transaction, per
the existing `HandleAsyncLeavesNoPartialPaymentOrCashTransactionWhenTheAllocationStepFails`
test), but only after an otherwise-avoidable Payment+CashTransaction
insert-then-rollback. Added a fail-fast plain-read check
(`GetByBillIdAsync` sum vs `bill.PayableAmount`) - positioned AFTER the
idempotency-replay check (an earlier draft placed it before, which broke
replay itself: a duplicate submit of an already-fully-allocated bill was
wrongly rejected as over-allocating). `AllocateAsync`'s own check remains
the authoritative, concurrency-safe guard; the new check is purely a
fail-fast optimization, verified not to change any test's asserted
outcome. All 6 ALKAROS.Cash.TenderHandler.Tests still pass; a new HTTP-level
test in V13-CSH-004's own suite
(`CashTenderClaimingMoreThanTheBillsRemainingPayableIsRejectedAndPersistsNothing`)
confirms the real route returns 409 OVER_ALLOCATION and a same-key retry
of the rejected request stays rejected (nothing was ever persisted for it).

## Scope executed
`src/Modules/Cash/TenderHandler/**`: a new, self-contained module implementing
the cash tender handler (PDF:I.26-I.29/I.49/II.2.7/II.5.9/III.9):
- CashTenderContracts.cs: CashTenderRequest/CashTenderResult. Deliberately
  its own shape, not ALKAROS.Payments.TenderRouting.TenderRequest (V13-PAY-002,
  out of this task's Owned surface) — cash needs strictly more than that
  generic envelope carries (tendered amount for change, which cash session
  it posts to, an idempotency key). Composing this into the generic
  router's shape is V13-PAY-003's own job (this task's Handoff).
- CashTenderExceptions.cs: CashTenderBillNotFoundException,
  ClosedCashSessionException, InsufficientCashTenderException.
- ICashTenderHandler.cs / CashTenderHandler.cs: the handler itself.
  - Validates the session is Open and the bill exists (plain reads before
    the write transaction opens).
  - Rejects TenderedAmount < AmountDue (InsufficientCashTenderException).
  - Opens ONE connection+transaction, takes a pg_advisory_xact_lock keyed
    on the request's own idempotency key (same pattern
    PostgresPaymentAllocationRepository already uses per-bill), checks for
    an existing allocation under that key first (idempotent replay - no
    new rows on a duplicate submit, not even a throwaway Payment), and
    otherwise creates the Payment (Initiated -> Tender -> Approve in
    memory, inserted once in its final Approved state with full status
    history), a CashTransaction (type Sale, amount = approved amount, the
    net cash retained in the drawer per docs/domain/cash-session-design.md
    §4's ExpectedCash formula), and the PaymentAllocation, all inside that
    same transaction, then commits once.
  - Change = TenderedAmount - AmountDue, returned in the result; never
    persisted as a separate record (Payment.ChangeAmount already carries
    it, per the Payment aggregate's own invariant).
- CashTenderHandlerModule.cs: its own IModule (same pattern as
  CashTransactionLedgerModule, keeps this task from ever writing to
  CashModule.cs), not yet added to ModuleRegistry.DefaultCatalog — none of
  this task's own dependencies (CashTransactionLedgerModule,
  PaymentAllocationPersistenceModule) are registered there either; wiring
  the full V1.3 composition into the live Host is V13-PAY-003's own job.
