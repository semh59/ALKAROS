## Scope executed
Splits the relay connector (RelayConnectorSupervisor + the cloudflared child
process it supervises, V12-QRT-001) out of the `api` container into its own
container, so the ONE component in this system actually reachable from the
public internet no longer shares a process/blast-radius with the rest of
the POS (Orders/Billing/Payments/Cash/Kitchen/...).

Two real problems were found and fixed during implementation (both via
real `docker compose`, not simulated — see below):

1. First attempt used `network_mode: "service:api"` to preserve
   V0-ARC-009's "Connector -> POS: Internal localhost" literally. Real
   testing found this coupled the two containers' lifecycles: restarting
   `api` also forced the connector to restart (Docker tears down/recreates
   a shared network namespace on the owner's restart), defeating half of
   this task's own point. Fixed by making the connector genuinely
   independent on the compose network, targeting `api` by its compose
   service DNS name (`http://api:5080`) instead of "localhost" -
   `RelayProvisioningService.LocalOriginService` changed accordingly.
   `docs/architecture/qr-relay-topology.md` (V0-ARC-009, a locked "Done"
   decision) got a dated, reasoned amendment note for this one line's
   mechanism (not its trust boundary/protocol/auth) - the decision itself
   was not deleted or reopened otherwise.

2. That fix broke a real, pre-existing security gate:
   `DualScreenApplication.cs` requires HTTPS on every request except a
   genuine loopback connection (the entire "unspoofable" argument for the
   NFC/QR relay's transport exemption was "nothing outside this container
   can present itself as a loopback peer"). Once the connector reached
   `api` over the compose bridge network instead of loopback, every real
   NFC/QR relay request started failing closed with 400 HTTPS_REQUIRED -
   a complete outage of the public ordering path, worse than the original
   problem. Fixed (user-approved) with a new, narrow, fixed-subnet Docker
   network (`relay-internal`, `172.28.90.0/28`) joined ONLY by `api`,
   `postgres` and `connector` — no other service — and a new
   `DualScreenOptions.NfcTrustedNetworks` / `--nfc-trusted-network` CLI
   flag extending the existing NFC-relay exemption check (OR'd with the
   still-honoured loopback check) to accept a source address inside that
   specific network. Same "unspoofable" shape as the loopback check it
   extends (only these three containers can ever be attached to it, by
   construction), verified this actually holds with a real request.
   Also found and fixed along the way: `connector` sharing TWO networks
   with `api` (`default` + `relay-internal`) made Docker's embedded DNS
   resolution of "api" ambiguous (it did not reliably return the
   `relay-internal` address) — fixed by putting `connector` on ONLY
   `relay-internal` and adding `postgres` to that same network too (so
   `connector` needs exactly one shared network with each peer it talks to).
