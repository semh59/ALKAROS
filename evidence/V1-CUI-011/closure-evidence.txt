## Real bugs found by this suite's own scenarios, root-caused and fixed
(same precedent as V1-WTR-026/027: an E2E suite exists to catch exactly this
class of defect, and fixing it in the same task the suite that found it
belongs to keeps the finding and the fix in one place)

1. Scenario 4 (and by extension every real walk-in Cashier sale) failed at
   submit with a 500: `DualScreenStore.StartOrderAsync` never set
   `Order.ServingUserId`, and `OrderSubmissionStockDispatcher.DispatchAsync`
   requires it ("Every Cashier/Waiter order is created with one; a null here
   means an order was constructed outside that path"). Fixed by threading
   the authenticated cashier's `principal.UserId` through both
   `StartOrderAsync` overloads and their two endpoints
   (`POST /terminals/{id}/orders` and `.../orders/table`) into the `new
   Order(...)` call. This was a REAL, currently-shipped defect: every
   PosTerminal Cashier walk-in sale ("Yeni sipariş aç") was already broken
   in production before this fix, confirmed via the real Host's own
   exception log (E2E_HOST_LOG=1), not by reading code.

2. Once (1) was fixed, comping an item on a submitted order made it vanish
   entirely from Order.Subtotal/DiscountTotal/TaxTotal/Total AND from the
   Kasa/customer-display line list, instead of showing "real price + a
   separate discount line" the way V1-RMD-228 already established for the
   Billing module's BillItem.cs. Root cause: `OrderItem.IsActive` (Draft or
   Active only) was reused by those four `Order` aggregate getters to decide
   which items to sum - a Complimentary item was silently excluded, as if
   never ordered. Fixed:
   - New `OrderItem.CountsInOrderTotals` (Draft/Active/Complimentary),
     `IsActive` itself left untouched (still gates kitchen re-fire and
     submission-time stock dispatch, which a post-submit comp can never
     reach anyway).
   - `Order.Subtotal/DiscountTotal/TaxTotal/Total` now use
     `CountsInOrderTotals`.
   - `ItemExceptionHandler.ApplyComplimentaryAsync`'s `compItem` now sets
     `discountAmount: targetItem.NetAmount + targetItem.DiscountAmount`
     (the full original net amount, now entirely discounted away) instead
     of passing `targetItem.DiscountAmount` through unchanged (typically 0)
     - the exact same formula `BillItem.FromOrderItem` already uses for a
     Complimentary line (V1-RMD-228).
   - `DualScreenStore.Display.cs`'s `GetSnapshotAsync` line query now
     includes `Complimentary` in its status filter (was `Draft`/`Active`
     only) and reconstructs a comped line's `LineTotal` from
     `unit_price * quantity * (1 + tax_rate/100)` instead of the persisted
     `gross_amount` (deliberately 0 for a comp, PDF:I.28.1/V0-DOM-006) - so
     the line renders at its real price on both Cashier.tsx and
     CustomerDisplay.tsx, with the discount surfaced only in the aggregate
     `discountTotal`.
