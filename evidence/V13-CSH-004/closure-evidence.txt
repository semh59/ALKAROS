## Why this task exists
Starting V13-PUI-002 (cashier CashSession UI) found that ICashSessionLifecycleService
(V13-CSH-001) and ICashTenderHandler (V13-CSH-003) had zero HTTP endpoints
and were not even registered in ModuleRegistry.DefaultCatalog - a UI cannot
call a backend that does not exist. Semih approved (PO:2026-09-18, via
AskUserQuestion in this session) opening a dedicated task for the
composition rather than silently expanding V13-PUI-002's own scope.

## Scope executed
New src/Host/DualScreen/DualScreenApplication.CashSession.cs (same file
pattern as DualScreenApplication.Screensaver.cs - a separate partial-class
file with its own MapCashSessionApi extension method):
- GET  /api/v1/terminals/{terminalId}/cash-sessions/suggested-opening-balance
- GET  /api/v1/terminals/{terminalId}/cash-sessions/active (404 when none open)
- POST /api/v1/terminals/{terminalId}/cash-sessions (Open)
- POST .../cash-sessions/{id}/start-count
- POST .../cash-sessions/{id}/counts (RecordCount)
- POST .../cash-sessions/{id}/close
- POST .../cash-sessions/{id}/reconcile
- POST .../cash-sessions/{id}/cash-tender (ICashTenderHandler)

All terminal-scoped, same cashier-cookie session (RequireCashierAsync)
every other Cashier route already uses.

A real bug found and fixed while wiring this: OpenSessionAsync itself
never posts an Opening CashTransaction (ICashSessionLifecycleService's own
doc comment already said as much - "V13-CSH-001 has no ledger yet... once
the ledger lands, the caller sums it instead"). Without the Open endpoint
also recording that entry, /close's own ComputeExpectedCashAsync would
have silently computed an expected cash of 0 for every session regardless
of what was actually floated. Fixed by recording the Opening entry
immediately after a successful open (skipped only when the opening
balance is exactly 0).
