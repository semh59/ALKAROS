## Scope executed
`src/Modules/Payments/Allocations/RefundIntents/**`: RefundIntent
eligibility/persistence, deliberately NOT the actual refund
(payment_reversals ledger, real Payment Approved/PartiallyRefunded/
Refunded transition, net-paid mutation) — all V13-ALC-004's own scope
(this task's Handoff, and this task's own Out of scope), which has not
landed yet:
- RefundIntent.cs: RefundIntentStatus (Pending/Rejected) and the
  RefundIntent entity — immutable except for its one Pending->Rejected
  transition (`Reject`). No Approve/Complete transition exists here; a
  fulfilled intent stays Pending in this table forever, its completion
  recorded entirely by V13-ALC-004's separate reversal ledger.
- RefundIntentExceptions.cs: InvalidRefundIntentAmountException,
  InvalidRefundIntentTransitionException,
  RefundIntentAllocationNotFoundException,
  RefundIntentCrossPaymentException, RefundIntentOverLimitException.
- RefundIntentFactory.cs: pure validation (no database) — same-payment
  invariant (an intent's target allocation must belong to the named
  payment) and the cumulative eligibility check: requestedAmount +
  already-Pending intents for that SAME allocation must not exceed the
  allocation's own amount. No payment_reversals table exists yet to also
  net against (V13-ALC-004's own table) - eligibility here is purely
  "already-Pending intents for this allocation".
- IRefundIntentRepository.cs / PostgresRefundIntentRepository.cs:
  CreateAsync — idempotency-replay first (a duplicate submit returns the
  existing row unchanged), then a per-allocation pg_advisory_xact_lock
  (same pattern PostgresPaymentAllocationRepository already uses
  per-bill) before computing the cumulative-Pending sum and calling the
  factory, so a genuinely concurrent duplicate submit still produces
  exactly one real row. GetByIdempotencyKeyAsync, GetByAllocationIdAsync,
  SaveAsync (persists the Reject transition, optimistic concurrency).
- RefundIntentsModule.cs: its own IModule (not yet added to
  ModuleRegistry.DefaultCatalog, same reasoning as V13-CSH-003/
  V13-ALC-002 — the full V1.3 composition is a later task's job).
- database/migrations/V13/V13-ALC-003/126-refund-intents.up.sql (+.down.sql):
  payments.refund_intents table — FKs to payments.payments and
  payments.payment_allocations, a CHECK tying Rejected status to
  rejected_at/rejection_reason both being set (and Pending to both being
  null), UNIQUE idempotency_key.
